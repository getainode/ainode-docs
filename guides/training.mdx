## Methods

| Method | Memory | When to use |
|---|---|---|
| **LoRA** | Low: bf16 base + adapters | Most fine-tunes |
| **QLoRA** | Lowest: 4-bit NF4 base + adapters | Large models on memory-constrained nodes |
| **Full** | High: all weights updated | Best quality, needs the whole model plus optimizer state in one node's memory |

Every run is **single node, on that node's own GPU**. Two templates were removed
in 0.5.27 because neither had a working implementation behind it, and each comes
back only together with one and a proven run:

| Removed | Why |
|---|---|
| `dpo-preference` | It offered chosen/rejected preference pairs, but there is no DPO trainer here: the runner would have space-joined prompt, chosen and rejected into one supervised string and trained the model **on the rejected answer** |
| `distributed-ddp` | It offered multi-node data parallelism, which has no launch path at all (the container-spawn build refuses it and the host `torchrun` path has no rendezvous), so the tile only ever produced a failed run |

The Distributed Training quick-start tile, the wizard's multi-node toggle and node
count, and the "Distributed Training" guide page went with them.

## How training runs

The orchestrator container is intentionally **slim** (no `torch`, `peft` or
`datasets`). When you submit a LoRA, QLoRA or full job (or an adapter
**merge**), AINode **spawns a GPU container** to run it: your model store is
mounted read-write, datasets read-only, the runner and container config are
staged into the job dir, and `peft` is pip-shimmed at launch. Cancelling a job
tears down the container.

### The training image

Training, merge and quantize jobs all run in the same GPU image, and **CI
publishes it** as of 0.5.28. A job resolves it in this order:

| Order | Image |
|---|---|
| 1 | `$AINODE_TRAIN_IMAGE` / `$AINODE_QUANT_IMAGE`, an operator's explicit override. A quantize job reads `AINODE_QUANT_IMAGE` first, a training job `AINODE_TRAIN_IMAGE` first |
| 2 | `ghcr.io/getainode/ainode-train:<this AINode version>`, the release image. Published, so a fresh node pulls it (about 8.6 GB to download, about 22 GB on disk) |
| 3 | `ainode-quant:0.17.0-t5`, the tag four Sparks built by hand in June 2026 and nothing else in the world has |

The release image is built by `.github/workflows/publish-train-image.yml` on a
`train-v*` tag or a manual dispatch, on the self-hosted aarch64 runner. An
`alias_versions` input lets one 22 GB build answer for several releases; an alias
tag re-uploads nothing.

Until 0.5.27 only (3) existed and CI published nothing, so every training,
quantize and merge job on a node that had not built it died with `docker` exit 125
and a log the operator had to decode. AINode now checks the image with
`docker image inspect` **before** launch, and the preflight error names all three
candidates with the pull, the build and the override:

```bash
docker build -f scripts/Dockerfile.quant -t ainode-quant:0.17.0-t5 .
```

A docker that is missing or not answering is reported as a broken docker, not as a
missing image.

### What a run does on a GB10

- The model is loaded with `attn_implementation: "eager"` by default. The
  training image's memory-efficient SDPA kernels are built for sm80 to sm100,
  and GB10 is sm121, so on this hardware SDPA returns zeros forward and NaN
  backward without raising. `"auto"` hands the choice back to transformers if
  you are on a GPU where SDPA works.
- Padding is dynamic per batch, and labels are masked to `-100` on padded
  positions, so the loss is over your text and not over pad tokens.
- Two gates fail the job rather than report success. HuggingFace's
  `logging_nan_inf_filter` is **off**, because it silently replaces a NaN loss
  with the running mean, which is how a dead run logged a tidy `loss: 0.0` for its
  last 20 steps. An `on_log` callback aborts the run with
  `AINODE_ERROR:NAN_LOSS`, naming the metric and the step, the moment loss or
  grad_norm goes NaN or inf, so nothing is saved. After a successful save the
  runner reads its own `*.safetensors` back and fails with
  `AINODE_ERROR:NAN_WEIGHTS` if any tensor holds a non-finite value, because the
  artifact is the only thing that speaks for the run.
- The first 20 steps are logged one by one, then at the configured cadence, so
  the loss chart in the browser is real where it matters.

<Note>
Why this exists: AINode had completed exactly one LoRA run in its life, and that
run's adapter was **100 percent NaN**, 2,162,688 of 2,162,688 values, merged into a
model with NaN in every q/k/v/o projection. Its `trainer_state.json` said what
happened and nobody read it: loss 12.61 at step 10, which is the uniform-random
baseline for that vocabulary (ln 151936 = 11.93), grad_norm 3.3 million, NaN from
step 20, and `COMPLETED` at the end.

Two independent faults, both reproduced on a Spark against the shipped runner
before anything was changed. The kernels refusing to launch on sm121 was one.
The other was tokenization padding every sequence to `max_seq_length` and copying
the padded `input_ids` into `labels`, so roughly 90 percent of the positions asked
the model to predict the pad token: that is where the 12.61 loss and the
six-orders-too-large gradient came from.

Same experiment, same node, same 20 steps: eager attention and masked labels give
loss 5.11 falling to 2.13 with grad_norm 8.2 at step 1, against the unchanged
runner's 11.93 and NaN.
</Note>

## Workflow

### 1. Add a dataset

AINode has a **Dataset Manager** (the **Datasets** tab in the Training view).
You can:

- **Upload** local files: JSONL, JSON, or CSV (`POST /api/datasets/upload`).
  The runner accepts these row shapes:

  ```jsonl
  {"text": "full training text"}
  {"instruction": "...", "output": "..."}
  {"prompt": "...", "completion": "..."}
  ```

- **Preview** samples before training (`GET /api/datasets/{id}/preview`)
- **Reference** any dataset in a run by its `dataset_id`
- **Delete** datasets you no longer need (`DELETE /api/datasets/{id}`)

You can also reference a Hugging Face dataset by ID (`tatsu-lab/alpaca`).

**Conversation rows work now.** AutoData writes `{"conversations": [...]}`, and
until 0.5.28 the runner had no branch for it, so the documented handoff died in
`dataset.map` with an IndexError and the `sharegpt-chat` template advertised the
same unusable shape. A dataset whose rows carry a `conversations` or a `messages`
column is rendered through `tokenizer.apply_chat_template`, with both spellings
mapped onto chat roles:

| Written as | Read as |
|---|---|
| ShareGPT / AutoData `from` + `value` | `role` + `content` |
| OpenAI `role` + `content` | As is |

Speaker names are mapped through an alias table (`human`, `prompter` to `user`;
`gpt`, `bot`, `model`, `chatgpt` to `assistant`; `function`, `observation` to
`tool`). Anything unrecognised is treated as a **user** turn, which is the safe
direction: it is supervised text either way, and it never claims the model said
something. A tokenizer with no chat template falls back to plain text.

<Warning>
**The whole rendered conversation is supervised**, the same way the
prompt/completion and instruction/output branches supervise their whole string.
Masking everything but the assistant turns needs per-turn tokenization of
template prefixes, which is template-dependent. It is not implemented, so nothing
claims it.
</Warning>

### 2. Launch the wizard

**Training** tab, then **New Training Run**, a 5-step wizard:
Base Model, Dataset, Method, Run Name, Review.

The wizard submits **canonical Hugging Face repo ids** (`org/name`). When you
train an on-disk model, the container builder maps its on-disk reference (an
`org--name` slug) to the right mount for you.

### 3. Monitor progress

Live loss chart, progress bar, log tail. Cancel anytime; the container is torn
down.

### 4. Retrieve artifacts

**View Output** on a completed run lists all files for download:
- `adapter_model.safetensors`
- `config.json`, `tokenizer.json`
- `checkpoint-N/` subdirs

### 5. Merge LoRA (optional)

Click **Merge Adapter** to merge LoRA weights into the base model via
`PEFT.merge_and_unload()`. The merged model can be loaded into vLLM. (This
action is state-gated and runs in the spawned GPU container.)

### Resume from a checkpoint

`POST /api/training/jobs/{id}/resume` works in container mode as of 0.5.28. It
accepts a failed, cancelled or completed job and answers **409** otherwise, picks
the highest `checkpoint-N` or the one you name in `{"checkpoint": "<name>"}`, and
creates a **new** job named `resume-<job_id>` with its **own** `output_dir` rather
than writing a second run's checkpoints into the first run's directory.

The whole source job dir is mounted **read-only at `/src`** and the checkpoint path
is rewritten into it. The 201 answer carries `resume_job_id`, `source_job_id`,
`checkpoint`, `checkpoint_path`, `output_dir`, `available_checkpoints` and
`status`; a launch the engine refuses answers 400.

Before that, the orchestrator's checkpoint path went to the container unchanged
with the source job dir unmounted, so HuggingFace answered "Can't find a valid
checkpoint".

## Jobs survive a restart

`TrainingManager` used to hold its jobs in memory only, so a restart emptied the
Runs table, zeroed the stats tiles, and 404'd merge, resume, logs and artifact
download for every earlier job while real job dirs sat on disk.

Each job now writes **`status.json`** into its own job dir at every transition (the
status setter does the write, because eight places move a job's status and one of
them forgetting is how the registry drifts from disk again), atomically, carrying
the status, the config with secrets stripped, when it was written, and a schema
version. The registry is rebuilt from the jobs directory at construction, and
nothing is started or adopted by that pass.

The jobs directory is the `training_dir` from **Config, Storage** when one is set,
and `<AINODE_HOME>/training/jobs` otherwise.

| Case | What happens |
|---|---|
| A job that was RUNNING or PENDING when the process stopped | Comes back **failed**, with a note saying the process did not survive the restart. A phantom RUNNING job blocks the queue |
| A job dir written before the release that added the status file | A best-effort verdict from what is on disk: completed if it left weights, failed otherwise; a quantize job judged by its checkpoint in the models store. Always with a `note` saying so, marked `restored`, and with **no `start_time`**, because the stats count GPU hours from it and a duration nobody recorded must not be invented |
| A directory with neither a status file nor a config | Not a job. That is what keeps thousands of empty dirs out of the history |

### The queue advances on its own

The queue used to advance only from a submit or a resume, so a second queued job
waited for a human to submit a third. A job's monitor now tells the manager when
its process exits, and a next job that cannot start is reported on the finished
job's log rather than raised out of the monitor task.

### A job the engine cannot launch is a 400

`TrainingJob.start()` used to set the job RUNNING and claim the active slot before
the launch command was even built, so a submit the engine refuses returned a 500
and left a phantom RUNNING job blocking every later job until someone deleted it by
hand. RUNNING, `start_time` and the active slot are now set only after `Popen`
returns a process, and a refusal marks the job failed while
`POST /api/training/jobs` answers **400** with the reason.

### The Hugging Face token stays out of job files and job logs

It used to be serialized into each job's `config.json` and
`config.container.json` (mode 644, in a directory the job API reads) and spelled
out as `-e HF_TOKEN=<token>` in the launch line appended to the job log that
`GET /api/training/jobs/{id}/logs` serves.

Training, quantize and merge now pass it through an `--env-file` written **0600**
and deleted when the container exits, the token is stripped from the config written
to disk, and every launch line is logged through one scrubber that masks secret env
values. A job's status is served by `GET /api/training/jobs` with auth off by
default, so the token is masked to `***` there too: the key stays, so a caller can
still see that a job has one.

## Configuration

| Parameter | Default | Notes |
|---|---|---|
| `num_epochs` | 3 | |
| `batch_size` | 4 | Reduce if OOM |
| `learning_rate` | 2e-4 | Use 5e-5 for full fine-tune |
| `lora_rank` | 16 | Higher = more capacity, more VRAM |
| `max_seq_length` | 2048 | Sequences are truncated to this; padding is per batch |
| `eval_split` | 0.1 | 0 to disable evaluation |
| `use_gradient_checkpointing` | false | Saves VRAM at the cost of speed |
| `attn_implementation` | `eager` | `auto` lets transformers pick (SDPA); keep `eager` on GB10 |
| `wandb_project` | (unset) | Enable W&B logging |

Click **Smart Defaults** in the wizard to auto-fill based on your model and
method.

## Gated models (Llama, Gemma)

```bash
ainode config --hf-token hf_xxxxxxxxxxxxxxxx
```

No restart is needed for training: the submit handler reads `hf_token` live
from the node config at job-submit time and passes it to the job container
through a mode-0600 env file that is removed when the container exits. The
token is never written into a job config or a job log, and the job status API
masks it. (A restart is only relevant for engine/serving, not training.)

## API

```bash
# Submit
curl -X POST http://localhost:3000/api/training/jobs \
  -d '{"base_model": "Qwen/Qwen2.5-7B-Instruct", "dataset_id": "<id>", "method": "lora"}'

# Status
curl http://localhost:3000/api/training/jobs/{job_id}

# List output files
curl http://localhost:3000/api/training/jobs/{job_id}/output

# Download adapter
curl -O http://localhost:3000/api/training/jobs/{job_id}/output/adapter_model.safetensors

# Merge LoRA into base
curl -X POST http://localhost:3000/api/training/jobs/{job_id}/merge
```

The full endpoint list, including datasets, is on the
[Training API](/api-reference/training) page.

## Troubleshooting

**Submit answers 400 naming `ainode-quant:0.17.0-t5`**: the node has not built
the training image. Build it with the command above.

**CUDA out of memory**: lower `batch_size` to 1 or 2, enable
`use_gradient_checkpointing`, or switch to QLoRA.

**`AINODE_ERROR:NAN_LOSS` at step 1**: the attention implementation is
producing NaN on this GPU. Leave `attn_implementation` at `eager` on GB10.

**401 from Hugging Face**: run `ainode config --hf-token hf_xxx`.

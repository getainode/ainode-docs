## Downloading models

Open the **Models** page. Four ways to add a model:

1. **Catalog**: 23 curated entries with launch recipes (engine image, flags, memory), click to download
2. **Search**: search Hugging Face live (`GET /api/models/search?q=`)
3. **Custom**: paste any HF repo ID (e.g. `microsoft/Phi-4`)
4. **Installed**: models already present on disk across your cluster (see below)

The **Custom** flow maps to `POST /api/models/download-repo`. Every download is
**commit-pinned**: AINode resolves a single commit sha for the whole snapshot up
front, so a repo pushed mid-download can never leave you with a mixed-commit
directory.

Downloads run in the background with a progress bar and are cancellable.
Downloads are parallel (`AINODE_DOWNLOAD_MAX_WORKERS`), per-file, and
cancel-checked between files, so a cancelled 15 GB pull stops promptly.

<Note>
Cancel posts to `POST /api/models/download-cancel`. In-flight downloads are
listed by `GET /api/models/downloads/active`.
</Note>

## Installed models

The Models page shows an **Installed models on your cluster** list: every model
present on disk on any node, not just entries that happen to be in the catalog.
Each installed model card exposes per-model actions:

- **Launch**: serve the model in vLLM (see below)
- **Unload**: stop a running instance (frees GPU memory, keeps the files)
- **Delete**: remove the on-disk snapshot (frees disk, see [Unload vs delete](#unload-vs-delete))

## Launching a model

From an installed model card, click **Launch Model**. The launch panel lets
you pick which **node(s)** to load on and (for stacked loads) set memory. Each
model runs as its own vLLM engine container, from the catalog recipe's
`engine_image` or the default `scitrera/dgx-spark-vllm:0.17.0-t5`. What happens
depends on how many models are already running:

- **First / solo load**: boots the primary engine at `:8000`.
- **Second concurrent load, stacked**: appends a **new vLLM instance** on the
  next free port (`8001`, `8002`, ...) **without restarting the primary**. Your
  first model keeps serving throughout.

The launch panel has **node toggles**. With one node picked, the load routes
through `POST /api/cluster/load` with that `{node_id}` (the master forwards it
to the node's own `/api/models/load` over the fabric). With several nodes
picked, the browser posts one `POST /api/sharding/launch` with the `node_ids`
and the model is launched across them with tensor parallelism; see
[Distributed Inference](/guides/distributed). The **Server** view also has a
**Load** button that does the single-node thing.

### Stacked loads: explicit memory + admission guard

Stacking a second model on a node has two hard requirements:

- You **must** pass an explicit `gpu_memory_utilization` for a stacked load.
  Omitting it returns **HTTP 400** (a default-sized second model can hard-crash
  a GB10 node's unified memory).
- The load is **admission-guarded**: if the node's projected *total* GMU across
  all instances would exceed **0.9**, the load is rejected with **HTTP 409**
  before any running instance is touched.

`gpu_memory_utilization` is clamped to the range **0.05 to 0.95** per load.
The node's primary counts toward the 0.9 total: the installer writes `0.6` for
it, which leaves 0.30 for one stacked neighbour.

### Per-load overrides

`POST /api/models/load` accepts optional overrides that are **persisted across
restarts** (they replay when the node cold-boots):

| Field | Purpose |
|---|---|
| `served_model_name` | One or more API aliases the model answers to |
| `max_model_len` | Context length override |
| `kv_cache_dtype` | KV cache dtype (e.g. `fp8`, `auto`) |
| `quantization` | Quantization method override |
| `trust_remote_code` | Allow custom modeling code |

<Warning>
Vision (VLM) models on GB10 must **not** use an fp8 KV cache: it corrupts
generation. AINode downgrades the fp8 default to `auto` for multimodal models
it can detect from the local `config.json`. For a model served straight from a
repo id before its weights are on disk, pass `kv_cache_dtype=auto` as a
per-load override.
</Warning>

## Unload vs delete

Two different actions, so keep them straight:

- **Unload** (`POST /api/models/unload`) stops a *running* instance and frees its
  GPU memory. Stacked instances each have their own unload control, so you can
  drop the model on `:8001` while the primary on `:8000` keeps serving. The
  on-disk files stay put.
- **Delete from disk** (`POST /api/models/delete-repo`) removes the snapshot from
  disk and frees the GB it occupied. Use this when you are done with a model
  entirely.

## Supported models

For the models we have actually launched through AINode and measured, with the
numbers and the gaps, see [Tested Models](/guides/tested-models).

Any model the engine image's vLLM can serve can be launched by repo id;
whether it comes up on your hardware is between vLLM, the checkpoint and the
GPU. The catalog carries **23 curated entries** across these families:

- Qwen (Qwen3.5, Qwen3.6, Qwen3.8, Qwen3-235B, Qwen3 Embedding)
- NVIDIA Nemotron (3.5 Lightning, Cascade 2)
- Ornith (Qwen3.5-MoE based)
- DeepSeek (V4 Flash)
- Meta Llama (3.1 8B, 3.1 405B, 3.3 70B)
- MiniMax (M2.7), GLM (5.1, 5.2 REAP)
- Spark-X2.5
- Whisper (speech to text)

### The `verified` rule

`verified: true` on its own says nothing a reader can check, so the flag is
**required** to carry the date it was proven and the bench record that proves it:

| Field | Meaning |
|---|---|
| `verified` | This recipe has actually served on this hardware. Drives the picker default and a check badge |
| `verified_on` | ISO date it was proven |
| `verified_record` | A filename under [`bench/results/`](https://github.com/getainode/ainode/tree/main/bench/results) |

A provenance test asserts over the whole catalog in **both** directions, so the
flag cannot appear without the record and the record cannot appear without the
flag. Six entries used to carry `verified` from before the bench existed with
nothing behind it; "verified" is what a user reads to decide whether a recipe will
come up on their hardware, so an entry nobody can check is worse than an honest
unverified one. They now say `verified: false`.

## The V100 lanes

Volta (SM70) was dropped from mainline vLLM in 0.20, so both V100 entries pin an
engine image that is **not a registry image**: the 1Cat-vLLM fork built locally
with SM70 kernels. Rebuilding takes about a day; moving one to another node is a
`docker save` of the tag.

### Qwen3.6 35B-A3B on one V100

`qwen3.6-35b-a3b-nvfp4-v100`, a frontier-shaped MoE (35B total, 3B active per
token, modelopt NVFP4) on a single Tesla V100 32 GB. 23.5 GB of weights,
`recommended_gmu` 0.90, 64K context, engine image `onecat-vllm:src-full`, served
text-only because the checkpoint's vision tower does not fit in 32 GB beside the
weights (two `--limit-mm-per-prompt` zeros keep it out of the budget).

Measured on pollux (Dell C4130, one V100 32 GB) on 2026-09-19: ready in 432
seconds, 30.4 of 32 GB used, 97 tok/s single-stream in the record, 344 tok/s
across 16 streams, decode still 66 tok/s at 63K prompt tokens. 20/22 on the quick
agentic rubric.

### Qwen3.8-Flash-Next at TP=4 on four V100s

`qwen3.8-flash-next-nvfp4-v100` is the same frontier MoE checkpoint as the GB10
entry (125B total, 6B active per token, plus a 51B PLE n-gram embedding and a 4B
MTP module), served on **one Dell C4130 across four Tesla V100 32 GB cards at
TP=4**. 133 GB against 4x32 GB leaves almost no headroom, which is why the
reservation is 0.94 and `--max-num-seqs` is 4. Engine image
`onecat-vllm:1.5.0-mm`, held only on castor.

Because the width is four cards inside **one** node rather than four nodes, the
catalog's `proven_tp` is 1 (it counts nodes) and the four-card width is stated in
the recipe as `--tensor-parallel-size 4`: a solo launch renders that flag only from
the recipe's extra args, so without it the engine would try to fit 126 GB on one
card.

MTP speculative decoding **is** on here, unlike the GB10 entry: the
`--enable-expert-parallel` flag that hangs on GB10 is not needed, so it never
comes up. This is the one place the V100 recipe is richer than the GB10 one.

Measured on castor on 2026-09-20 through AINode: ready in 855 seconds, 126.7 of
128.0 GB used at peak, 49.6 tok/s single-stream with a 285 ms TTFT, 65.3 tok/s
sustained over 1500 tokens, 92.5 tok/s with thinking off, 104.2 tok/s across 16
streams, prefill flat near 2150 tok/s out to 118K prompt tokens with decode still
at 52.8. The engine reports a mean acceptance length near 3.0 at a 50 percent
draft acceptance rate.

<Warning>
**Address this lane by its catalog id.** It shares the repo
`nvidia/Qwen3.8-Flash-Next-NVFP4` with the GB10 entry, and a load posted as the
repo id resolves to that one (a GB10 nightly image, TP=2, the mp shape), which is
not runnable on Volta. A catalog id wins over an HF repo in recipe resolution
precisely so an id can name one of two lanes sharing a checkpoint.
</Warning>

## Speech

`whisper-large-v3-turbo` (`openai/whisper-large-v3-turbo`) is in the catalog with
capability **`speech`**: 809M parameters, 99 languages, transcription only. 1.6 GB
of weights and a 448-token decoder window, so at `recommended_gmu` 0.06 it stacks
beside a chat model and one instance serves every node.

It pins `ghcr.io/getainode/ainode-whisper:0.17.0-t5`, which is the stock GB10
build plus `librosa` and `soundfile`. No image on the fleet ships them, and vLLM
imports `soundfile` at module scope as soon as the served model reports the
transcription task, so the stock image dies at startup before it binds a port.
The recipe also states `--enforce-eager` and `kv_cache_dtype: auto` rather than
inheriting a node's fp8 default, because fp8 KV buys nothing across a 448-token
window and is not a combination anyone has proven on an encoder-decoder model
here.

That image is published by CI (`.github/workflows/publish-whisper-image.yml`, from
`scripts/Dockerfile.whisper`, on a `whisper-v*` tag or a manual dispatch), so
LAUNCH works on a node that has never built anything. Its tag is the **base engine
image's** tag rather than an AINode version, because the image tracks the engine
it derives from and an AINode release does not rebuild it.

### It is verified now, with a record

The entry carries `verified: true` since 0.5.30, and the record it names is a
speech bench run rather than a claim. Measured on Spark-4 (an ASUS GX10) on
2026-09-21, stacked at `0.06` beside Nemotron 3.5 Lightning at `0.62` and the
embedder at `0.06`, so all three shared one GB10:

| Measurement | Result |
|---|---|
| Ready | 110 seconds, which the entry carries as `typical_ready_minutes: 2.0` |
| Word error rate | 2.3 percent over 10 clips in 6 voices and 6 English locales, 4.6 percent orthographic |
| Word for word | 8 of the 10 clips |
| Latency | 739 ms median per clip, through the fleet endpoint |
| Real-time factor | 0.18, so it transcribes about five times faster than the audio plays |

The record is
[`20260921-012724-whisper-large-v3-turbo-spark-4-stacked-beside-nemotron-at-0_62-via-the-fleet-endpoint-speech.json`](https://github.com/getainode/ainode/blob/main/bench/results/20260921-012724-whisper-large-v3-turbo-spark-4-stacked-beside-nemotron-at-0_62-via-the-fleet-endpoint-speech.json),
and the numbers are on [Tested Models](/guides/tested-models).

<Warning>
**Warm the engine before pointing a user at it.** On `--enforce-eager` the first
transcription after a launch compiles the kernels. Measured by hand on Spark-4 it
took **89 seconds**, against 0.7 for every one after it. The speech bench takes one
untimed warm-up request for exactly this reason and records it rather than hiding
it, so a cold engine cannot quietly become a latency number.
</Warning>

Turbo is a **transcription** model and cannot translate; vLLM's own note says so.
`/v1/audio/translations` is proxied for the ASR models that can. See
[Audio](/api-reference/audio) for the API.

A speech instance is its own kind across the interface: it stays out of the chat
and bench pickers the way an embedding instance does, and the capability probe
reports `speech` off the catalog rather than asking a chat question of an engine
with no chat path.

## Shared storage across cluster

To avoid downloading the same model on every node, mount a shared NFS path and
point `models_dir` at it on each node:

```json
// ~/.ainode/config.json on each node
{
  "models_dir": "/mnt/shared-models"
}
```

Shared NFS storage is the recommended default when you want a single copy of each
model visible fleet-wide. (Alternatively, each node can keep its own on-disk copy
and serve it locally; a multi-node launch ships the head's copy to a peer that
lacks it.) See [Cluster Setup](/cluster-setup) for cluster configuration.

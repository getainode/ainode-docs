## When the cluster helps (and when it does not)

GB10 decode is **memory-bandwidth bound**, not compute bound. That shapes what
spreading a model across nodes buys you:

- **A model that does not fit one node.** Tensor parallelism pools the nodes'
  memory. Every multi-node launch measured here is a Mixture-of-Experts model,
  because an MoE needs the pooled memory for its total parameters but reads
  only its active parameters per token, so decode stays usable:
  - DeepSeek V4 Flash (284B / 13B active), 2x GB10 at TP=2: 34.5 tok/s
    single-stream, 94.0 tok/s across 16 streams
    (`20260916-033415-deepseek-v4-flash-dspark-fp8-tp2-mp.json`).
  - Qwen3.8-Flash-Next NVFP4 (125B / 6B active), 2x GB10 at TP=2: 26.2 tok/s
    single-stream, 207.6 tok/s across 16 streams
    (`20260916-204216-qwen3_8-flash-next-nvfp4-tp2-mp-nightly.json`).
  - Qwen3-235B-A22B NVFP4, 4x GB10 at TP=4: 16.5 tok/s single-stream
    (`20260617-000000-qwen3-235b-a22b-nvfp4-tp4-frontier-moe.json`, measured on
    AINode 0.4.x).
- **Batched multi-user throughput** across nodes, through the federated master
  (see [Federated Serving](/guides/federation)).

<Warning>
Multi-node tensor parallelism does **not** make single-stream decode faster.
Every layer adds all-reduces over the fabric, and the comms cost eats the
per-node bandwidth gain. A model that fits on one node should run **TP=1**.
Reach for the cluster to gain *capacity*, not single-stream *latency*. There is
no measured number here for a dense 70B or 405B model, on one node or across
several; the catalog's 405B entries have never been served.
</Warning>

## How it works

A multi-node launch is **one `vllm serve` container per node**, using vLLM's
own multi-node executor (the `mp` shape in `distributed_executor`):

1. The head resolves the selected peers to their fabric IPs.
2. Over SSH, the head starts an engine container on each peer with
   `--node-rank k --headless`, and makes sure the peer has the weights and the
   compiled-kernel cache it needs.
3. The head starts its own engine container as rank 0 with
   `--tensor-parallel-size N` and `--nnodes N`.
4. All ranks rendezvous on `--master-addr <head fabric IP>` and `--master-port`
   (29501, plus an offset for a stacked distributed instance), and the head's
   engine serves on its API port.

Each node holds `1/N` of the weights (or its share of the experts). All-reduce
collectives run over NCCL; the NCCL library is whatever the engine image
ships, and AINode sets its environment (`NCCL_SOCKET_IFNAME`,
`GLOO_SOCKET_IFNAME`, `UCX_NET_DEVICES`, `NCCL_IB_HCA`) on every engine
container from `cluster_interface` and the node's RDMA devices.

There is no Ray cluster in this path and no external launcher script. Nothing
is needed in the engine image beyond vLLM. A `"ray"` value of
`distributed_executor` also exists in the code (a `ray start --head` container
plus SSH-launched Ray workers), but it requires the `ray` CLI inside the
engine image, and no image AINode ships or pins has one, so it is not a shape
you can launch today. Both proven multi-node catalog recipes pin `mp`.

Only **tensor parallelism** exists. The launch body accepts a `strategy` field
for compatibility, and any launch spanning more than one node is tensor
parallel; there is no pipeline parallelism.

### Flags the engine gets

You never hand-edit vLLM commands. The head builds the `vllm serve` argument
list from the catalog recipe (`engine_image`, `extra_vllm_args`,
`gpu_memory_utilization`, `kv_cache_dtype`, `max_model_len`) and the
rendezvous flags above. Some notes on what that means in practice:

- `--kv-cache-dtype` defaults to `fp8`, and is downgraded to `auto` for vision
  models unless you ask for fp8 explicitly. A recipe can pin either.
- `--enforce-eager` is added only when the instance runs the pinned default
  engine image (`scitrera/dgx-spark-vllm:0.17.0-t5`), where it works around a
  CUDA-graph fault on GB10. Recipes on `vllm/vllm-openai:v0.27.1` and later do
  not get it: it disables CUDA graphs and costs throughput there.
- `gpu_memory_utilization` comes from the recipe or the launch body. The code
  default is 0.5; the installer writes 0.6 for the node's primary.
- RoCE (RDMA) is used when the ConnectX-7 devices are visible: AINode maps
  `/dev/infiniband` into the engine container and whitelists the node's HCAs.
  Without them NCCL falls back to sockets over `cluster_interface`.

## Launch from the browser

The launch panel's **node toggles** drive multi-node launches. The head node
is pinned; toggle the peer dots to add nodes. With more than one node
selected, the browser posts one `POST /api/sharding/launch` with `model` and
the chosen `node_ids`. A curated multi-node recipe (DeepSeek V4 Flash,
Qwen3.8-Flash-Next) fills in the engine image, the flags and the `mp` shape, so
the launch is one click. A node that is not an online member, or that
broadcasts no fabric IP, is refused with 422 before anything starts.

`GET /api/sharding/plan?model=<id>` previews what the launch would look like on
the nodes available, and `GET /api/sharding/status` reports the distributed
instances on this node.

The alternative is configuration: set `distributed_mode: "head"` and explicit
fabric `peer_ips` in the head's `config.json`, then `sudo systemctl restart
ainode`.

<Note>
A multi-node launch takes longer than a solo one. Peers may compile kernels on
first launch, and the bind wait allows a launch that is still making progress
up to 3600 s (`engine_bind_ceiling_seconds`). A distributed instance is not
replayed automatically after a restart of the head; relaunch it.
</Note>

## One fabric NIC per node

Each node should have exactly **one NIC with an IP on the cluster subnet**, and
`cluster_interface` in `config.json` should name it. AINode pins
`NCCL_SOCKET_IFNAME` and `GLOO_SOCKET_IFNAME` to that interface on the engine
container, so a second NIC on the same subnet is an ambiguity you do not want
at rendezvous time.

```bash
# Verify: should show exactly one IP on your cluster subnet
ip addr | grep "10.0.0\|192.168.0"
```

## NCCL transport verification

After launching a distributed model, check the engine log. As of the current
release `ainode logs` follows the log the configured backend writes
(`nvidia-distributed.log` on a distributed head) and prints which file it is
tailing. The exact log strings depend on the transport NCCL selects on your
fabric; verify against your own launch rather than trusting these literally:

```bash
ainode logs -f | grep "Using network"
# Good:  a RoCE/IB transport line naming your NIC + link speed
# Bad:   "Using network Socket", much slower; check the ConnectX-7 cabling
```

## GPU Direct RDMA (optional, advanced)

An optional speedup that depends on the host driver state:

```bash
# Load the peermem module on each host (not in the container)
sudo modprobe nvidia-peermem

# Verify NCCL picks it up on the next launch
ainode logs -f | grep "GPU Direct RDMA"
```

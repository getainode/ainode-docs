A cluster doesn't have to shard one giant model across every node. With
**federation**, each node serves its own model(s), and the **master** routes each
`/v1/*` request to the node currently serving the requested model — a single
OpenAI-compatible endpoint in front of the whole fleet.

<Note>
Federation (one endpoint, many models, routed by name) is distinct from
**distributed tensor-parallel** (one model sharded across nodes — see
[Distributed Inference](/guides/distributed)). Use federation to serve many models
across a fleet; use TP to serve one model too big for a single node.
</Note>

## How routing works

The master builds a routing table from live cluster broadcast state — every node
advertises its primary model and any stacked instances it heads. When a `/v1/*`
request arrives:

1. The master reads the `model` field of the request body.
2. It collects **every** node currently serving that model (local node first, then
   remote peers over the fabric).
3. It forwards to the first candidate and **fails over** to the next if a target is
   mid-swap, crashed, or otherwise unreachable.

Failover is what makes routing robust: a crashed node is indistinguishable from a
live one in cluster state, so the master uses a fast connect-timeout (5s) and moves
on to the next candidate rather than hanging the request.

- If **no node** serves the requested model, the master returns `404`
  (`model_not_found`).
- If every candidate is unreachable, it returns `502`.

`GET /v1/models` returns the **union** of models served across the fleet, so an
OpenAI client sees one catalog. Point your client at the master's `/v1` endpoint and
set `model` to the exact id (or a `served_model_name` alias) you loaded.

## Model stacking is routed too

A single node can hold **more than one model at a time**. Each stacked instance gets
its own port (`8001`, `8002`, …) and its own `served_model_name` alias(es). The
router treats stacked instances as first-class routing targets — a co-resident
second model on a node lives at `:8001`, not the node's primary `:8000`, and the
master routes to it by name.

Stacked instances **persist across restarts** — AINode replays them on boot so your
fleet comes back exactly as you left it — and loads are **serialized** so two models
never race for the same memory. A specific stacked instance is also reachable
directly on its own port.

<Tip>
Since 0.5.1, `GET /api/nodes` carries a per-node `instances[]` list (primary +
every stacked model with its port and status), and the dashboard renders a
**STACKED** sub-card per instance with its own **Unload** control — the same source
the router uses, so the views and routing always agree.
</Tip>

## Load or unload any node from the browser

You manage the whole fleet from one browser tab — no SSH. `POST /api/cluster/load`
and `POST /api/cluster/unload` take a `{node_id, model}` and the master **forwards
the call over the fabric** to that node's local `/api/models/load` / `unload`
endpoint. The master never SSHes into a peer; it reuses each node's own model API.

```bash
# Load a model on a specific node
curl -X POST http://localhost:3000/api/cluster/load \
  -H 'Content-Type: application/json' \
  -d '{"node_id": "spark-2", "model": "Qwen/Qwen3-9B-AWQ", "gpu_memory_utilization": 0.4}'

# Unload it later
curl -X POST http://localhost:3000/api/cluster/unload \
  -H 'Content-Type: application/json' \
  -d '{"node_id": "spark-2", "model": "Qwen/Qwen3-9B-AWQ"}'

# See the fleet — nodes, primary models, and stacked instances[]
curl http://localhost:3000/api/nodes

# The federated model catalog (union across all nodes)
curl http://localhost:3000/v1/models
```

<Warning>
A second-or-later model on a node **must** specify `gpu_memory_utilization`
explicitly (the node default could push total reservation past capacity and hard-
crash a GB10 — unified memory). The admission guard rejects a stacked load whose
projected node total would exceed the `0.90` cap, and it runs **before** the live
instance is touched. See [Troubleshooting → Stacked loads](/troubleshooting).
</Warning>

## Per-node memory headroom

Each node exposes a **memory-utilization** knob so you can leave room for a second
stacked model or for a quantization job (which needs the node's full unified memory
— see [Quantize a Model](/guides/quantize)). Set `gpu_memory_utilization` on the
load request; the launch form surfaces it as an input and validates it on
distributed loads too.

## Send a request through the master

```python
from openai import OpenAI

client = OpenAI(base_url="http://localhost:3000/v1", api_key="not-needed")

resp = client.chat.completions.create(
    model="Qwen/Qwen3-9B-AWQ",   # routed to whichever node serves it
    messages=[{"role": "user", "content": "Hello from the fleet"}],
)
print(resp.choices[0].message.content)
```

The master resolves `model` to the serving node, streams the response back, and
records the request against fleet metrics — all transparent to the client.

<Info>
Federated routing, `/api/nodes` `instances[]`, and the STACKED dashboard sub-cards
are all live as of **0.5.2**. If your fleet predates them, run `ainode update`.
</Info>

## What "tested" means here

A model is on this page only if all three of these are true:

1. **It was launched through AINode**, not with a hand-written `docker run`. If we
   served it raw, outside the product, it does not count.
2. **Somebody measured it on our own hardware** and the numbers below are what the
   engine reported, not a vendor slide and not an extrapolation.
3. **The run is committed** as a JSON record in
   [`bench/results/`](https://github.com/getainode/ainode/tree/main/bench/results)
   in the product repo, so you can read the exact node, engine image, vLLM flags
   and settings behind every number.

Everything else is untested, and this page says so out loud. Absence of a model
here is not a claim that it fails; it is a claim that we have not measured it.

<Note>
The six tables below are generated from those JSON files by
`scripts/render-bench-table.py` in the product repo, so the page cannot drift
from the data. A measurement nobody took renders as **not measured** rather
than as a zero or a guess. If a table here lags the README in the product repo,
the README is newer.
</Note>

**Single-stream tok/s** is decode speed for one request at a time. **16 streams
tok/s** is the aggregate across 16 concurrent requests, which is the number an
agent or multi-user workload actually gets. **Rubric** is a correctness pass, not
a speed one: a fresh agent drives the served endpoint through executed code,
parallel tool calls, and needle retrieval at three context depths, with thinking
on and off. Click the run label to read the full record.

A few results that the table cannot hold:

- **Qwen3.6 35B-A3B NVFP4 on a Tesla V100** is the first model launched through
  AINode's own launch path on Volta hardware: pollux, a Dell C4130 with one
  V100 32 GB, on a 1Cat-vLLM engine image with Volta kernels. 97.4 tok/s
  single-stream and 343.9 tok/s across 16 streams, decode still 66.2 tok/s at
  63K prompt tokens.
- **Nemotron 3.5 Lightning 30B-A3B** reproduces NVIDIA's 500+ tok/s claim at 16
  streams, with DSpark speculative decode accepting 55 to 61 percent of drafted
  tokens. With thinking off it answers in about 0.1 s, which makes it the right
  model for plumbing calls.
- **Qwen3.8 27B** is dense, so it is bandwidth-bound on GB10: 19.0 tok/s with
  Qwen3.5 MTP speculative decode against 11.8 tok/s without it. OCR on it needs
  `temperature 0`, and it must not run with an fp8 KV cache
  (see [Vision Models](/guides/vision-models)).
- **Ornith 1.5 35B-A3B** was measured as a *stacked* second instance at
  `gpu_memory_utilization=0.26`, not as the only model on its node. Decode over
  depth: 40.0 tok/s at 4K prompt tokens down to 34.4 tok/s at 120K, with TTFT
  going from 194 ms to 136 s. Prefill is capped around 880 tok/s at 120K because
  speculative decode pins `max_num_batched_tokens` at 2048.
- **DeepSeek V4 Flash** and **Qwen3.8-Flash-Next** are the two-node rows: each
  launched by AINode across Spark-2 and Spark-3 with the `mp` shape from its
  catalog recipe, at TP=2 over RoCE.
- **Qwen3-235B-A22B** is the four-node row: TP=4 across four GB10 nodes at
  16.5 tok/s single-stream, surviving a 3,513-token prefill, measured on AINode
  0.4.x with `--enforce-eager`, which that engine image needed.

## Embedding runs

An embedding model is served the same way every chat model is, by vLLM on the
same engine image with `--runner pooling`, stacked beside a chat model, and
`POST /v1/embeddings` on any node routes to it by model id. **Dims** is the vector
width read off the response. **p50 ms** is one short text embedded on its own,
end to end from where the bench ran; the record carries the measured transport
floor beside it (32.1 ms on the first run against a 71.6 ms p50). **Texts/s at
64** and **Tokens/s** are the batch-64 row of the sweep. **Pairs ordered** asks
whether every related pair beats every unrelated one, a sanity check, not a

## Speech runs

A transcription model writes no tokens: audio goes in, and what comes back is
scored against words nobody typed at it. It is served the way every other model
here is, by vLLM on the engine image its catalog recipe pins, so it stacks beside
a chat model on one GPU and `POST /v1/audio/transcriptions` on any node routes to
it by the model id in the multipart body.

**WER** is the word error rate against the exact text the clips were made from,
**pooled over words** rather than averaged over clips. It folds number words to
digits, so a transcript that heard every word and wrote "9" for "nine" is not
called wrong for its spelling. The bracketed rate beside it is the **orthographic**
one, which folds only case, punctuation and whitespace, and is the mean of the
per-clip rates rather than a pooled figure. The gap between them is how much of the
error was spelling rather than hearing. **Exact** counts the clips that came back
word for word. **p50 ms** is one clip uploaded on its own, end to end from wherever
the bench ran, and **RTF** is the real-time factor, wall seconds per second of
audio, so below 1 means the engine transcribes faster than the clip plays.

The audio is ten committed WAVs in
[`bench/speech/clips/`](https://github.com/getainode/ainode/tree/main/bench/speech/clips),
six voices across six English locales, every line carrying digits and most a place
or product name, because a wrong number and a wrong name are where transcription
goes wrong in a way a user notices. A word error rate is only comparable over the
same bytes, so the clips are committed rather than fetched, and the reference is
the exact text they were generated from rather than anything transcribed by hand.

## Run the bench yourself

The bench is pure inference load against the OpenAI-compatible endpoint. It is
non-destructive: it launches nothing, unloads nothing, and writes nothing on the
node. Two entry points, same code:

- **From the browser**: the Bench view runs it against whatever is loaded on the
  fleet (`POST /api/bench/runs`; see the [Bench API](/api-reference/bench)).
- **From a terminal**: `scripts/ainode-bench.py` in the product repo. It needs
  only the standard library and writes a schema-1 record into the repo's
  `bench/results/`.

```bash
git clone https://github.com/getainode/ainode && cd ainode

# One run: single-stream, prefill, sustained decode, a concurrency sweep and the
# reasoning tax, written out as a schema-1 record under bench/results/.
python3 scripts/ainode-bench.py \
    --url http://<node-ip>:3000 \
    --model unsloth/Qwen3.8-27B-NVFP4 \
    --ainode http://<node-ip>:3000 \
    --label mtp-vision

# Pretty-print a saved record
python3 scripts/ainode-bench.py --show bench/results/<file>.json
```

`--only single,prefill,sustained,concurrency,reasoning` picks sections;
`--depths` and `--streams` set the sweep points. The subcommands measure the
other sections: `ainode-bench harness` (a coding agent driving the model to
passing tests), `ainode-bench agentic` (the agentic rubric), `ainode-bench decide`
(the decision bench), `ainode-bench embed` (the embedding bench) and
`ainode-bench speech` (the speech bench). Each has `--help`.

```bash
# The speech bench, against a Whisper instance anywhere in the fleet
python3 scripts/ainode-bench.py speech \
    --endpoint http://<node-ip>:3000/v1 \
    --ainode http://<node-ip>:3000 \
    --model openai/whisper-large-v3-turbo \
    --label "stacked beside a chat model"
```

`--translate` measures `/v1/audio/translations` instead, `--language` pins the
language, and `--generate-clips` rebuilds the committed WAVs on a Mac, which is a
maintenance step rather than part of a run.

On a node that [requires an API key](/security/api-keys), every section takes
`--api-key` or reads `AINODE_API_KEY`, and a 401 or a 429 stops the section before
it scores anything. See [Bench API](/api-reference/bench). The record format is in
[`bench/SCHEMA.md`](https://github.com/getainode/ainode/blob/main/bench/SCHEMA.md):
one JSON file per run, named `<stamp>-<model-slug>-<label>.json`, where a run is
one model on one placement (node, engine image, flags) on one day.

Two rules keep the numbers honest, and the harness enforces both. Token counts
come from the server's own `usage` block, never from a local tokenizer estimate,
so a bad chars-per-token guess cannot move a result. And every depth request
carries a unique nonce at the **front** of the prompt, so `--enable-prefix-caching`
cannot serve a cached prefill and make deep context look free.

<Warning>
Point the bench at the AINode API port (`:3000`), not at an engine's own port. Run
it from a machine on the same network as the node, and do not run it against a
node that is serving real traffic: a 16-stream sweep will contend with it.
</Warning>

## Submit a result

We will take results on hardware we do not own. Open a pull request against
[getainode/ainode](https://github.com/getainode/ainode) with:

1. **One JSON file** in `bench/results/`, named
   `<stamp>-<model-slug>-<label>.json`, matching
   [`bench/SCHEMA.md`](https://github.com/getainode/ainode/blob/main/bench/SCHEMA.md).
   Fill in `placement` completely: node, GPU, GPU count, TP degree, engine image,
   AINode version, and the vLLM flags the engine actually ran with.
2. **Nothing else edited by hand.** Run `python3 scripts/render-bench-table.py`
   and commit the README change it makes. A test fails if the table and the JSON
   disagree.
3. **Omissions, not estimates.** Leave out any section you did not measure. A
   missing key renders as "not measured", which is the answer we want. Filling it
   with a plausible number is the one thing that will get a result rejected.
4. **The rubric only if you ran it.** `rubric` is pass and total counts from a
   correctness pass, not a self-assessment.

If the model was served raw rather than launched through AINode, say so in `notes`
and in the pull request. We would still like to see it, and we will label it as
what it is.

## Before you install

The installer enforces one hard prerequisite:

- **`/mnt/shared-models` must exist**, or the installer aborts. Create it first (for a cluster, mount shared model storage there; NFS from the master is recommended):
  ```bash
  sudo mkdir -p /mnt/shared-models
  ```

<Note>
**Two images, no NGC login.** AINode is a slim orchestrator image
(`ghcr.io/getainode/ainode:<version>`) plus one vLLM engine container per
loaded model. The engine image is the catalog recipe's `engine_image`, or
`scitrera/dgx-spark-vllm:0.17.0-t5` from Docker Hub, which pulls anonymously.
The installer pre-pulls that default engine image (about 8.5 GB to download,
about 22 GB on disk); set `AINODE_NVIDIA_IMAGE=skip` to defer it to the first
model launch, or `AINODE_NVIDIA_IMAGE=<image>` to pre-pull a different one.
</Note>

## Single node

```bash
curl -fsSL https://ainode.dev/install | bash
```

## Multi-node cluster

```bash
# On the head node: bootstraps passwordless SSH to each peer (ssh-copy-id, you may be prompted once)
AINODE_PEERS="10.0.0.2,10.0.0.3" curl -fsSL https://ainode.dev/install | bash -s -- --job master

# On each worker node
curl -fsSL https://ainode.dev/install | bash -s -- --job worker
```

`AINODE_PEERS` only takes effect together with `--job master`. Without a
`--job`, the node is installed **solo**: the peer list is used for
`ssh-copy-id` and nothing else, and `peer_ips` in `config.json` stays empty.
Give the fabric addresses of the peers (the ConnectX-7 subnet), not management
LAN or Tailscale addresses; a multi-node launch runs over those.

A worker starts with no model and no engine. It announces itself over UDP and
waits for the master to launch something on it.

## Node roles

| Flag | Role | Behavior |
|---|---|---|
| `--job master` | Head node | Runs its own engine, manages the cluster, heads multi-node launches |
| `--job worker` | Worker node | No model, no engine at start; waits for the master |
| _(none)_ | Solo | Standalone, no clustering |

Under the hood these map to the node's `distributed_mode` config field: master
maps to `head`, worker to `member`, solo to `solo`.

Change role after install:

```bash
ainode role master   # or worker / solo
sudo systemctl restart ainode
```

## Uninstall

```bash
curl -fsSL https://ainode.dev/uninstall | bash               # keeps ~/.ainode data
curl -fsSL https://ainode.dev/uninstall | bash -s -- --purge  # deletes everything
```

<Warning>
Use `bash -s -- --purge`, not `bash --purge`. With `bash --purge` the flag is
consumed by `bash` itself (not the piped script), so it is silently ignored and
your data is **not** purged.
</Warning>

## Container image

The AINode image is published to GHCR only:

```bash
docker pull ghcr.io/getainode/ainode:<version>    # pin a numeric tag
```

<Tip>
The installer deliberately resolves and pins the highest numeric tag rather than
`:latest`, because `:latest` has drifted to old builds in the past. If you pull
manually, pin a numeric tag too. The current tags are on the
[releases page](https://github.com/getainode/ainode/releases).
</Tip>

## What gets installed

| Path | Purpose |
|---|---|
| `/etc/systemd/system/ainode.service` | Systemd unit, auto-starts on boot; carries `Environment=AINODE_HOME=<install user's ~/.ainode>` |
| `/usr/local/bin/ainode` | Host wrapper CLI (`ainode update` runs on the host; other commands are forwarded to the container) |
| `~/.ainode/config.json` | Node configuration |
| `~/.ainode/image.env` | Pinned container image tag (`EnvironmentFile` the unit reads; rewritten by `ainode update`) |
| `~/.ainode/models/` | Downloaded model weights |
| `~/.ainode/datasets/` | Training / AutoData datasets |
| `~/.ainode/logs/` | Engine logs (`nvidia-vllm.log`, or `nvidia-distributed.log` on a distributed head) |
| `~/.ainode/training/` | Fine-tune artifacts |

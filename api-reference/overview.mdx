## Base URLs

Port **3000** is the AINode aiohttp app: the management API, the Prometheus
exposition, and an OpenAI-compatible proxy that federates across the whole
cluster. Port **8000** is the primary vLLM engine container on this one node
(stacked instances take 8001, 8002, ...).

| Purpose | URL |
|---|---|
| Inference (OpenAI-compatible, cluster-federated) | `http://localhost:3000/v1` |
| Inference (raw primary vLLM engine, this node only) | `http://localhost:8000/v1` |
| Management API | `http://localhost:3000/api` |
| Prometheus metrics (`ainode_*`) | `http://localhost:3000/metrics` |

<Note>
Always target port **3000** for inference. The proxy routes each request to
whichever node serves the requested model and fails over if a node drops.
Port `8000/v1` only ever sees the one engine, is closed until a model is loaded,
and `8000/api/*` is a 404. Likewise `http://localhost:8000/metrics` emits
vLLM's own `vllm:*` metrics, not the documented `ainode_*` set; those are on
`3000/metrics`.
</Note>

## Authentication

**On by default since 0.5.30.** A fresh install mints one key, requires it, and
prints it once at the end of the install; `AINODE_AUTH=off` at install time keeps
the previous open node. An install over an existing config changes neither the state
nor the keys.

```bash
ainode auth status                       # is it on, how many keys
ainode auth key create --name <client>   # mint a key for one client, printed once
ainode auth key list                     # which client holds which key
ainode auth key revoke <id>              # take one away
ainode auth enable | ainode auth disable # require a key, or stop requiring one
```

Every one of those is live: the server re-reads `auth.json` when it changes, so
nothing needs a restart. Or use the dashboard, under **Config, API access**, which
also shows the keys that exist with a Revoke on each and takes a pasted key on a
fresh browser.

With auth on, **every path under `/api` and `/v1` needs the key**, as
`Authorization: Bearer <key>`. Five paths and the static shell stay open; see
[API keys](/security/api-keys) for the list and the reason for each. `/metrics`
is not one of them.

Nodes authenticate to each other with a key derived from the cluster's shared
secret, so a whole fleet can run with auth on and a joined node needs no key of its
own.

| Endpoint | Description |
|---|---|
| `GET /api/auth/status` | Whether API-key auth is on, and how many keys exist (never a key or a hash). Answers without a key |
| `POST /api/auth/enable` | Turn API-key auth on. Returns the minted key once, or `key: null` when the node already had one |
| `POST /api/auth/disable` | Turn it off |
| `GET /api/auth/keys` | The key ids |
| `POST /api/auth/keys` | Create a key; the value is returned once |
| `DELETE /api/auth/keys/{key_id}` | Revoke a key |

`GET /api/status` carries an `auth` block whose `label` is the sentence the
dashboard chip shows: `API key required`, `API open, key set but not required`, or
`API open, no key set`.

## Transport

Plain HTTP on port 3000 by default. `ainode tls enable` adds an HTTPS listener on
**3443** and leaves 3000 exactly where it was, and
`ainode tls enable --tailscale` gets a real Let's Encrypt certificate for the
node's tailnet name in one command, with a host timer that renews it. A node that
serves HTTPS says so in `tls`, `tls_port` and an `https` `url` on
`/api/cluster/endpoint` and `endpoint_hint`. See [TLS](/security/tls).

Per-client rate limits on `/v1` are available and off by default. See
[Rate limits](/security/rate-limits).

## Inference endpoints

The AINode proxy on port **3000** serves these with cross-node routing and
failover, keyed on the body's `model`. Details on [Chat & Completions](/api-reference/chat).

| Endpoint | Method | Description |
|---|---|---|
| `/v1/chat/completions` | POST | Chat completions (streaming supported) |
| `/v1/completions` | POST | Text completions |
| `/v1/embeddings` | POST | Embeddings, routed fleet-wide to a vLLM pooling instance serving the requested embedding model |
| `/v1/messages` | POST | Anthropic Messages shape, forwarded by the same proxy as chat completions (query strings such as `?beta=true` are forwarded) |
| `/v1/messages/count_tokens` | POST | Token count for an Anthropic-shaped body, through the same proxy |
| `/v1/decide` | POST | Typed questions in, probabilities out: a state, an optional instruction, and a map of questions; every question is answered at once with `answer`, `confidence`, `distribution` and `latency_ms`. Not a forwarded path: it composes several grammar-constrained chat completions of its own, and routes with the proxy's candidate list |
| `/v1/responses` | POST | The OpenAI Responses API. Streams |
| `/tokenize` | POST | Token ids for a prompt or a chat body. **Not under `/v1`**, because vLLM does not serve it there. Answered by chat and pooling engines alike |
| `/detokenize` | POST | Text back from token ids. Also not under `/v1` |
| `/v1/rerank` | POST | Rerank documents against a query. A pooling-model path, so it lives on an embedding engine |
| `/v1/score` | POST | Score pairs. Also a pooling-model path |
| `/v1/audio/transcriptions` | POST | Speech to text. **multipart/form-data**, with the model in a `model` form field. See [Audio](/api-reference/audio) |
| `/v1/audio/translations` | POST | The same, translating into English |
| `/v1/models` | GET | On `3000`: the federated union of models across the fleet. On `8000`: only that engine's model |

The five paths from `/v1/responses` through `/v1/score` were added in 0.5.27.
Port 3000 answered 404 for all five before that, so a caller who wanted a token
count, a Responses call or a rerank had to abandon fleet routing and address one
engine's port directly, losing the model-id lookup and the failover with it. The
list is what `curl http://<node>:<port>/openapi.json` returns on the fleet,
checked against vLLM 0.27.1 (chat) and the 0.17.0 pooling engine stacked beside it,
so nothing is registered that an engine would 404 anyway.

### `/v1/embeddings` is routed by its own handler

It is not on the shared proxy, because it validates the body before forwarding: a
request without a JSON object carrying a string `model` is a **400**. It then
reuses the proxy's candidate list, posts the verbatim body with failover on
transport errors, and returns every HTTP status untouched. When no node can be
reached it answers **502** with `no reachable node is serving '<model>'`. Only when
nothing in the fleet serves that id at all does it fall back to the in-process
sentence-transformers manager, which on the shipped container image answers **503**
`dependency_missing`.

<Warning>
Two consequences of that separate handler, both open as
[issue #241](https://github.com/getainode/ainode/issues/241): the embeddings hop
does **not** set `X-AINode-Served-By`, and it does **not** read the pinning headers
or the body field. Everything below about pinning and `X-AINode-Served-By` applies
to the eleven paths on the shared proxy, not to `/v1/embeddings`.
</Warning>

### Pinning a request to one instance

With the same model on two nodes, routing on the model id alone picks the local
hop first, so the answer could come from an engine you did not choose. Pin it:

| Where | What |
|---|---|
| `X-AINode-Node: <node_id>` | Pin the node. With no port, its primary engine port |
| `X-AINode-Port: <port>` | Pin the port. With no node, a stacked instance on this node |
| `"ainode_target": "<node_id>:<port>"` in the body | The same pin as a body field. Stripped before forwarding, because it is AINode's field and not vLLM's |

A pin is honoured **exactly**: one candidate, **no failover**, because the point of
pinning is that the answer is attributable to that engine. An unknown node id is a
**404** with `"code": "unknown_node"`, never a quiet fall back to the local engine.

**Every response from the shared proxy carries `X-AINode-Served-By: host:port`**,
naming the instance that actually answered, on both the streaming and the
non-streaming path, and the header is listed in `Access-Control-Expose-Headers` so
a browser can read it. The chat view records it per turn instead of echoing the
pick.

The host is the literal `localhost` for the local hop and the peer's `fabric_ip`
for a remote one, so a local answer reads `localhost:8000`.

### Candidate ordering

With nothing pinned, a request goes to the members whose status is online,
serving or member-ready: **this node first** (its primary port, then each stacked
instance's port), then the remote peers in cluster order. With no candidate at all
the answer is a **404** `model_not_found` naming the model, when the fleet has
members.

Candidates are **reordered by capability only for a multimodal request**: a chat
completions or Messages body whose `messages` carry an `image_url`,
`input_audio`, `video_url` or `file` part, or an Anthropic `image` or `document`
block. Instances known to serve vision go first, never-probed ones next, and known
refusers are dropped; when nothing is left the answer is a **400** with
`"code": "no_multimodal_instance"`. A live 400 from an engine that says it accepts
no images is recorded in the capability cache and failed over.

That ordering therefore never fires for `/v1/responses` (whose body uses `input`),
`/tokenize`, `/detokenize`, `/v1/rerank` or `/v1/score`.

## Management endpoints

| Endpoint | Description |
|---|---|
| `GET /api/status` | Node status, GPU info, engine state. Carries `engine_adopted`, true when the engine on this node's own port survived the last restart rather than being relaunched ([adoption](/cluster/adoption)) |
| `GET /api/health` | Liveness check, and the one route that answers with no key. `{"status": "ok", "version": "<running release>"}`, which is what `ainode update` verifies against |
| `GET /api/nodes` | All discovered cluster nodes (incl. per-node `instances[]`, each carrying `adopted` on a clustered node) |
| `GET /api/cluster/info` | Cluster topology |
| `GET /api/cluster/resources` | Aggregated memory + GPU counts across the cluster. A multi-GPU node counts as all of its GPUs (`gpu_count` off the announcement) |
| `POST /api/cluster/load` | Load a model on any one node (`{node_id, model, ...}`) |
| `POST /api/cluster/unload` | Unload a model on any node (`{node_id, model}`) |
| `POST /api/sharding/launch` | Launch one model across several nodes (`{model, node_ids}`); see [Cluster API](/api-reference/cluster) |
| `GET /api/sharding/status` | The distributed instances on this node |
| `GET /api/cluster/endpoint` | The fleet's addresses: this node, the master, every online member. **Needs no API key.** See [Surviving the master](/cluster/endpoint) |
| `POST /api/cluster/join` | Join a node using a token. On the **master**, and the one other route that needs no API key. See [Joining a node](/cluster/joining) |
| `POST /api/cluster/join-self` | The same join performed by the joiner, behind the key rule |
| `POST /api/cluster/update-all` | Cluster-wide pull + image swap (workers first, master last, over HTTP) |
| `GET /api/cluster/update-status` | Live per-node update progress |
| `POST /api/cluster/role` | Set this node's cluster/distributed role |
| `POST /api/cluster/id` | Set this node's cluster id |
| `GET /api/metrics` | JSON metrics snapshot |
| `GET /api/metrics/history` | Any retained series over any window, for this node or, with `?node=<id or name>`, any node in the fleet. See [Metrics retention](/ops/metrics-retention) |
| `GET /metrics` | Prometheus text exposition (`ainode_*`) |
| `POST /api/engine/set-model` | **Destructive boot-config route.** It stops whatever the node is serving, including stacked instances it has no accounting of, and with no engine object at all it saves the config and starts nothing. Nothing in the UI calls it; use `POST /api/cluster/load` |
| `POST /api/engine/update` | Pull a target image, pin it, and self-restart onto it |
| `GET /api/version/check` | Check for a newer version on GHCR |
| `GET /api/config` | Read node config |
| `PATCH /api/config` | Update node config |

### Server view

The Server view's console, one node at a time.

| Endpoint | Description |
|---|---|
| `GET /api/server/status` | Every engine instance on this node: model, port, whether it is stacked, its type (`chat` or `embed`) and its capabilities |
| `GET /api/server/endpoints` | The endpoints this node serves, with the port each is on |
| `GET /api/server/logs` | The orchestrator log |
| `DELETE /api/server/logs` | Clear it |
| `POST /api/server/models/{model_id}/eject` | Stop one instance and leave the rest running |

<Note>
The browser onboarding wizard and its three `/api/onboarding/*` routes were
removed in 0.5.29. No deployed node could reach them: the installer writes
`"onboarded": true` and every non-TTY start sets it before the server binds, so
`/onboarding` answered a redirect to a page that redirected straight back. Joining
is [`ainode join`](/cluster/joining) and a card in **Config, Cluster**. The
terminal wizard on a TTY `ainode start` is unchanged.
</Note>

<Note>
The deploy path is `POST /api/cluster/update-all` (or
`ainode update [version]`, run as the service user). It pulls `ghcr.io/getainode/ainode:<version>`
on every node over HTTP, workers first, master last, no SSH, and each node
swaps to the new image via its swappable systemd unit.
</Note>

## `POST /api/engine/update`

Pull a target image and swap this node to it.

- Body (optional): `{"version": "<version>"}`. Omit it to resolve and pull the
  highest numeric GHCR tag anonymously.
- On a successful `docker pull`, AINode writes `~/.ainode/image.env` (read by
  the swappable systemd unit via `EnvironmentFile`), then `docker stop`s
  itself so `Restart=always` relaunches the container on the new image.
- It only self-restarts when the container was launched by the swappable unit
  (`AINODE_UNIT_SWAPPABLE=1`). On a node still running a pre-swappable unit it
  pins the image and returns `{"status": "pulled", "restarted": false, ...}`
  with a message telling the operator to migrate the unit (re-run the
  installer).
- A pull failure returns HTTP **502** and does **not** write `image.env` or
  restart; the node keeps running its current image.

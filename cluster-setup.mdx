## Overview

AINode discovers peers automatically over UDP broadcast on the discovery port in
`config.json` (the installer writes 5679). The primary multi-node mode is a
**federated master**: each node serves its own model(s) solo, and the master
routes `/v1/*` requests to the node holding the requested model. You load and
unload any model on any node from the master UI.

The master can also **launch one model across several nodes** with tensor
parallelism over NCCL. That is for a model that does not fit on a single node,
in practice a large MoE. A model that fits on one node should run TP=1:
cross-node tensor parallelism adds all-reduces over the fabric on every layer
and does not make single-stream decode faster.

**Measured through AINode's launch path:** four GB10 nodes (3x DGX Spark + 1x
ASUS GX10) as a federated fleet, TP=2 pairs, and one TP=4 launch. The records
are on [Tested Models](/guides/tested-models).

## Step 1: Install on each node

```bash
# Master node (AINODE_PEERS bootstraps SSH to the peers; give their fabric addresses)
AINODE_PEERS="10.0.0.2,10.0.0.3" curl -fsSL https://ainode.dev/install | bash -s -- --job master

# Each worker node
curl -fsSL https://ainode.dev/install | bash -s -- --job worker
```

Every node should run the same AINode release. Without `-s -- --job master`,
`AINODE_PEERS` gives you a solo node with SSH keys copied and nothing else.

### Or join an existing cluster with one command

On a cluster that already exists, do not hand-edit the new node's `config.json`.
Mint a token on the master and paste one line on the new box:

```bash
ainode cluster token                     # on the master
ainode join <master-host>:3000 <token>   # on the new node
```

That writes the cluster id, the cluster secret, the master's address, the discovery
port and the member role, and restarts the service. `AINODE_JOIN` does it as part of
the install. See [Joining a node](/cluster/joining).

## Step 2: Open the cluster UI

Navigate to `http://<master-ip>:3000` and open the **Cluster** tab. Nodes
appear as they start broadcasting.

## Step 3: Load a model on one node, or launch one across several

From the launch panel:

1. Pick the model (catalog entry or Hugging Face repo ID).
2. Use the **node toggles** to choose where it runs. The head node is pinned;
   toggle the peer dots to add nodes.
3. Set **`gpu_memory_utilization`** in the per-load input (required for a
   stacked second load on a node).
4. Launch.

With one node selected, the browser posts `POST /api/cluster/load` with that
`node_id`, and the master forwards the call over the fabric to the node's own
`/api/models/load`. With several nodes selected, it posts one
`POST /api/sharding/launch` with the chosen `node_ids`. The head is always this
node; the other nodes are resolved to their fabric IPs (a node with no known
fabric IP is refused with 422). A curated multi-node catalog recipe supplies the
engine image, the vLLM flags and the executor shape, so the launch is one
click. The mechanism is described on [Distributed Inference](/guides/distributed).

The alternative to the UI is `distributed_mode: "head"` plus explicit `peer_ips`
in the head's `config.json`, then `sudo systemctl restart ainode`.

## Network requirements

| Requirement | Why |
|---|---|
| Passwordless SSH from the head to each peer | The head SSHes into each peer to start that peer's engine container |
| A fabric NIC per node, named in `cluster_interface` | AINode sets `NCCL_SOCKET_IFNAME`, `GLOO_SOCKET_IFNAME`, `UCX_NET_DEVICES` and `NCCL_IB_HCA` on the engine container from it |
| UDP discovery port (installer default 5679) open on the cluster subnet | Peer discovery |
| TCP 29501 (plus an offset per stacked instance) between nodes | The multi-node rendezvous port (`--master-port`); the engine containers run with host networking |

<Warning>
Use the direct fabric NIC (ConnectX-7 / `enP2p1s0f1np1`) for NCCL, not
Tailscale. Tailscale adds milliseconds of RTT on every collective.
</Warning>

## Memory reference

GB10 decode is memory-bandwidth bound, so the cluster pays off on **MoE** models
(which read only their active parameters per token), on batched multi-user
throughput, and on capacity, not on making a dense model decode faster.

| Nodes | Aggregated memory (UI sum) | Measured here |
|---|---|---|
| 1x GB10 | about 122 GB usable (128 GB unified) | Dense up to 27B and A3B-class MoE at TP=1, stacked two per node |
| 2x GB10 | about 244 GB | DeepSeek V4 Flash at TP=2: 34.5 tok/s single-stream, 94.0 tok/s at 16 streams (`20260916-033415-deepseek-v4-flash-dspark-fp8-tp2-mp.json`); Qwen3.8-Flash-Next at TP=2: 26.2 / 207.6 tok/s (`20260916-204216-qwen3_8-flash-next-nvfp4-tp2-mp-nightly.json`) |
| 4x GB10 | about 487 GB | Qwen3-235B-A22B NVFP4 at TP=4: 16.5 tok/s single-stream (`20260617-000000-qwen3-235b-a22b-nvfp4-tp4-frontier-moe.json`, measured on 0.4.x) |

Every number above cites its record under
[`bench/results/`](https://github.com/getainode/ainode/tree/main/bench/results).
There is no measured number for a dense 70B or 405B model on this hardware.

## Troubleshooting

**NCCL using socket transport instead of RoCE**  
Check with `ainode logs -f | grep "Using network"` (as of the current release
`ainode logs` follows the log the configured backend writes, and prints which
file). It should name an IB/RoCE transport. If it says `Socket`, the mlx5
driver is not loaded or the ConnectX-7 port is not on the cluster fabric.

**A multi-node launch is refused with 422**  
A selected node is not an online member, or it broadcasts no fabric IP. Set
`cluster_interface` in that node's `config.json` and restart it.

**Workers not appearing in topology**  
Run `ainode doctor` on both nodes first: it checks the discovery port, the cluster
id, the peers it can see and their versions. All nodes must be on the same broadcast
domain (same L2 subnet), share the same `cluster_id`, and share the same
`cluster_secret`, because two nodes installed independently each generate their own
and are invisible to each other. See [Signed discovery](/security/discovery).

**The fleet is running two releases**  
Every node announces its version, and the dashboard draws a banner naming each
release and the nodes on it. See [Versions on the wire](/cluster/versions).

**A head came back without its multi-node model**  
It adopts the engine container it is still running, relaunches the recorded shape
once when every peer answers an ssh probe, or marks the record degraded and names
the peer that did not. See [A head across a restart](/cluster/head-restart).

AINode is a free, open-source platform that turns an NVIDIA GPU machine into a local AI stack: a browser chat UI, an OpenAI-compatible API, LoRA fine-tuning, and a federated multi-node master that routes each request to the node serving the requested model, or launches one model across several nodes with tensor parallelism over NCCL.

**One command to install. No cloud. No monthly bill.**

```bash
curl -fsSL https://ainode.dev/install | bash
```

### Proven, with a record

Every row below has at least one run committed under
[`bench/results/`](https://github.com/getainode/ainode/tree/main/bench/results)
in the product repo, launched through AINode's own launch path. The full
tables are on [Tested Models](/guides/tested-models).

| Hardware | GPU | Memory | What ran | Record |
|---|---|---|---|---|
| NVIDIA DGX Spark | GB10 | 128 GB unified (about 122 GB usable) | Solo, stacked, and TP=2 / TP=4 multi-node serving | `20260913-130400-ornith-1_5-35b-a3b-nvfp4-text-only-mtp.json`, `20260916-033415-deepseek-v4-flash-dspark-fp8-tp2-mp.json`, `20260617-000000-qwen3-235b-a22b-nvfp4-tp4-frontier-moe.json` |
| ASUS Ascent GX10 | GB10 | 128 GB unified | Solo and stacked serving, embeddings | `20260813-000000-nvidia-nemotron-3_5-lightning-30b-a3b-nvfp4-dspark-recipe.json`, `20260919-220011-qwen3-embedding-0_6b-spark-4-stacked-beside-nemotron-embed.json` |
| Dell C4130 | 1x Tesla V100 32 GB | 32 GB HBM2 | Solo serving through the catalog (a Volta-specific engine image) | `20260919-040456-qwen3_6-35b-a3b-nvfp4-pollux-v100-solo-onecat-src-full.json` |

GB10 nodes are linked to each other over their ConnectX-7 QSFP ports (RoCE).
There is no NVLink bridge between nodes in this product.

### Expected to work, untested

- **Dell Pro Max with GB10** and **HP ZGX Nano AI Station** share the GB10 part
  with the DGX Spark and the GX10, so the same engine image should run on them.
  Nobody has run AINode on either yet.
- **Any other Linux machine with an NVIDIA GPU and a CUDA driver** is a design
  goal, not a verified claim. The default engine image
  (`scitrera/dgx-spark-vllm:0.17.0-t5`) is an aarch64 GB10 build; a different GPU
  needs a different engine image, set through `NVIDIA_VLLM_IMAGE` or a catalog
  recipe's `engine_image`. The V100 row above is the one example of that so far.

If you run AINode on hardware not listed here, measure it and
[send us the record](/guides/tested-models).

## Architecture

A node runs **two images at minimum**: the slim AINode orchestrator, and one
engine container per loaded model.

```
ghcr.io/getainode/ainode:<version>     pinned tag, resolved and pulled by the installer
         |  (slim Python orchestrator: no torch, no vLLM, no CUDA in this image)
         |
         +-- aiohttp app on port 3000: web UI, /v1 proxy with routing + failover,
         |   /api management, /metrics (ainode_*)
         +-- engine launcher: one vLLM engine CONTAINER per loaded model,
         |   started over the mounted Docker socket
         |       image = the catalog recipe's engine_image, else
         |               scitrera/dgx-spark-vllm:0.17.0-t5 (Docker Hub, no login)
         |       primary on port 8000, stacked instances on 8001, 8002, ...
         +-- UDP discovery broadcaster (the discovery port in config.json; the installer writes 5679)
         +-- training / quantization: a spawned GPU container from a locally built image
```

The installer resolves the **highest numeric GHCR tag**, pulls that pinned
image (never a floating `:latest`, which it only falls back to when tag
resolution fails), writes the tag to `~/.ainode/image.env`, and pre-pulls the
engine image the code will launch. Every node in a cluster should run the same
AINode image. There is no Docker Hub mirror of the AINode image; GHCR is the
only registry.

The engine backend is `"nvidia"` by default: the engine is its own container,
so nothing in the orchestrator image has to carry vLLM. An older `"eugr"`
backend (eugr/spark-vllm-docker's launcher plus a `vllm` binary on PATH) is
still selectable by name in `config.json`, but nothing shipped provides those
pieces, so a node installed the documented way uses `nvidia`.

The systemd unit reads the pinned tag from `image.env` through an
`EnvironmentFile` and runs with `Restart=always`, so a node survives a cold
power cycle and replays its models on boot. Upgrading is `ainode update`, run
as the service user: it resolves and pulls the newest numeric tag, rewrites
`image.env`, and restarts (see [Updating AINode](/guides/update)).
